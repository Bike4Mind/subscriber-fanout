# subscriber-fanout - Design Notes

Goal: The client subscribes to MongoDB queries in order to replicate the backend database into the client.

General plan:

- Client adds a `useCollectionQuery(collection, mongoQuery)` hook, which kicks off a query and returns matching records
- The query initially gathers data from the in-browser database, and simultaneously opens a query to the backend for data.
- The backend processes these queries and arranges for ongoing change stream results to be delivered to the client.

## Client Handling

The client exposes a hook, `useCollectionQuery(collection, mongoQuery)`, which returns the records pertinent to the query.  It arranges for a query with the websocket backend, then returns the reactive result-set for a query against IndexedDB.

Once the query has subscribed to the backend, it begins receiving records, starting with any existing records in the database which match the query.  As the client receives these records, it'll insert them into the local database.  Once inserted, they'll be returned by the query which requested them.

## Server handling

We need to have _some_ long-running process going, to consume the change-stream.  Therefore, we implement a long-running backend, subscriber-fanout, which issues queries to MongoDB, listens to the resulting change streams, and sends changes to interested clients.

Thinking through the subscription lifecycle:

- Client makes a websocket request which goes to a Lambda Function, `subscribe_query`, to arrange the subscription
- This function queries for the query requested, then associates a normalized form of the query with destination socket ID.  There may be multiple subscribers to the same query.  These associations are stored in MongoDB itself.
- Our long-running process monitors mongo's querySubscriptions collection for new queries to monitor, and as they're added/created, our process begins monitoring them.  Initially, it monitors all queries, but in the future we may provide a load-balancing mechanism between multiple instances of our long-running process.
- Having subscribed to the query of interest, the long-running process receives updates and dispatches them to subscribers.  It opens one change stream per collection rather than per query (each stream costs the server a full oplog scan), and matches each change against every query on that collection in process with `mingo`.  A query or projection the matcher cannot evaluate exactly as MongoDB would (see `src/matcher.ts`) falls back to a dedicated per-query stream, which filters on the server but otherwise skips, retries, resumes, replays and reopens after a drop or rename like a shared one.  A query MongoDB rejects keeps its dedicated stream reopening with backoff, logged at `error` on each try, and delivers nothing.
- As it does so, if any of the subscribers have disconnected and throws an error, we remove it from the subscription list.  Once the subscription list becomes empty, we drop the subscription.
- Delivery, memory and slow clients are covered in the next section.

## Delivery and memory

A POST is one `PostToConnection` request, carrying a whole message or one chunk of a chunked one; the rules below are per POST.  Latencies and cut thresholds are timed from the moment the POST has a connected socket, so DNS lookup, TCP and TLS setup never count toward them; the connect and request timers are in Sending.  A connection's latency L is an EWMA (alpha 0.2) of its completed POSTs, and it keeps its last 16 durations in each frame size class (up to 32 KB, over 32 KB); the largest of those is its own p99 in that class.  u is the time its current POST has spent in flight, summed over cut attempts.  L' is L, or the smaller of L and its latest completed POST when that POST was under the slow line, and L* = max(L', u).  Ref is the k-th fastest of the connections' latest completed POSTs, k = min(10, ceil(n/10)), over the n connections whose latest POST completed within max(10s, 2 x R), R being the smoothed healthy rotation (see Sending); it is recomputed at most once a second, and is 0 with no such connection.  The slow line is max(1s, 2 x Ref).  A connection is slow when L* is over the slow line, and slow by L when both L and its latest completed POST are over it.  A suspect is slow but not slow by L, which means it is slow only through the attempt it has in flight.  A connection is healthy when it has completed a POST and is not slow, and new otherwise.  A client that answers every POST within 1s is never slow.

### Budget

- The heap E counts each event once, from read until its last delivery settles and it has left the replay buffer, each looked-up document (see Streams), 150 B per delivery plus 56 B per connection, and 320 B per connection with sends queued.  The bodies X count each body (below) from its build until its last POST settles.  The stored bytes are E + X, held at the budget B: the read and match gates keep E within C = 1.25 x B plus one change's match overhead per stream (see Admission), and the body gate keeps X within B plus one body.  Pings are not gated: they hold one delivery's overhead per connection, about 10.5 MB at 20k idle connections.  The frame bytes are held at F = B/4: each POST in flight counts its frame's length plus 24 KB for the request state it holds.  Released requests (see Sending) count up to 32 MB outside F.
- `B = max(16 MB, min(256 MB, (heap limit - used) / 3))`.  used is the heap after a GC once startup has loaded the subscriptions, plus m for each subscription added since, where m is the heap per subscription measured over that load.  B is recomputed when the subscription count changes by 10%.  The other two thirds of the free heap cover the frames, overshoot, driver replies and GC headroom.
- Sizing: the heap limit needs to be at least the heap after startup (about 30 MB plus m per subscription, m being about 10.6 KB with typical queries) plus 3 x B, and the container about twice the heap limit.  20k subscriptions at B = 16 MB need about a 600 MB container.
- At startup the fanout logs B, the heap, m, the largest document it delivers (about B/3) and S.  When the heap limit is under the heap after startup plus 3 x B, whether B was computed or set with `maxQueuedBytes`, it logs an error naming the heap limit needed, and again if a later rise in subscriptions makes the heap short.  A startup load counts the subscriptions first, and once 1000 are loaded it projects the heap the rest will take at the same size each; when that would leave less than the 16 MB floor it logs an error naming the heap limit needed, so a load too large for the heap is reported before it runs out.

### Admission

- One walk over each change sizes it before it is normalized: its heap (the change plus the objects of its normalized copy, which shares the change's strings, so each string counts once, at 1 B per character when every code unit is at most 0xFF, else 2 B) and the JSON size of its document, which bounds any projection's body.  The walk also copies out any Binary whose backing buffer is over twice its length and over 4 KB, since the driver reads a Binary as a view of the whole reply it came in.
- An event whose heap plus JSON size is over B cannot be delivered within the budget.  It is skipped with a `warn` and its resume token persisted, as is an event over 16 MB.
- The read gate takes an event only when E plus its heap stays within the line: C, or, while a stream has been paused 10s or more, that stream's resume line (see Pausing).  Before the check, replay-only events are evicted while the stored bytes are over B.  A refused event is not charged: its stream pauses and reads it again when it resumes, so waiting for room holds nothing.  Bodies never refuse a read directly, but a match waiting for a body holds its event in E, so E can climb to the line and refuse reads.
- The read gate charges a change its own heap; the overhead of its deliveries is charged at match, and O_s is what stream s's matches charged and has not released.  The match gate holds a stream's next change, or next replay step, while E is over C and the stream's own O_s is above 0, and wakes it when its O_s reaches 0 or E falls to C.  Unmatched changes hold no overhead, so a stream with O_s at 0 always matches, even a change whose overhead alone is over C, and one stream's slow deliveries never hold another stream's matching.  O_s falls only as the stream's deliveries settle or their connections close, each with its own bounded exit: the request timeout, a released request's answer or timeout, and the 60s of sending time.  Pings belong to no stream and hold no gate.  A change already started, such as one waiting at the body gate or for a lookup, resumes without the gate.  Past C each stream adds at most one change, so E stays within C plus one change's overhead per stream (150 B per subscription it matches plus 56 B per connection), plus 320 B per connection with sends queued.  That sum is at most every subscription matching once, about 10.5 MB at 20k single-subscriber subscriptions.  A replay walk is gated once per slice, so one slice can add up to a replay window's match overhead: at most 500 events to the walking subscription's subscribers.  A wide stream whose changes match few subscriptions charges little at match, so it keeps reading whole batches.

### Bodies

- One body is built per event and projection (the subscription's `fields` as JSON, so the same fields in another order build another body): the message from `"collectionName"` on.  Each message is the subscriber's prefix `{"action":"data_update","subscriptionId":...,` followed by the body, byte-identical to earlier versions.  Bodies and prefixes are Buffers allocated on their own, not as slices of Node's shared 64 KB slab, which a held slice would keep alive whole.  Chunk frames are cut per send from prefix and body at UTF-8 boundaries, with a fresh `_chunkId` per message send, so a connection holds one frame at a time.
- A body is built at match and charged at its real size.  It is built when the stored bytes are within B, or when X plus the event's JSON size stays within B; otherwise the match waits mid-event, holding its event, while the deliveries it already queued keep sending.  Over B, builds go in the order they asked, across streams; once the stored bytes are within B, every waiting build tries again.  A waiting build leaves the line as soon as its next try ends without waiting again, as when the body was built by another stream or the subscription or its subscribers are gone, and when its stream closes.  X falls only as deliveries settle and connections close, and neither waits on matching or reading.  The projected document is dropped once the body is built, and the body is freed when the last delivery of its event and projection settles.

### Matching

- Each stream queues the changes it reads, and one loop matches the queued changes of every stream, a change at a time from each stream in turn, in slices of at most 5ms with POSTs and their callbacks running between slices.  A change's delivery to a subscription is queued for sending as soon as that subscription matches it.  A paused stream keeps matching the changes it has read.
- Matching agrees with MongoDB, except that a `Long` or `Decimal128` value with no exact double fails closed under range operators and negations: it matches none of them in process, even where MongoDB would.
- A stream stops reading while more than 1000 changes wait to be matched, or while they would take over 20s at its average matching time, and reads again once both are under half; both are logged.  Waiting changes are never evicted.
- A subscription or subscriber that joins is replayed the buffered changes from a second before it joined (its `createdAt`) that the matcher has already passed, including one being matched as it joins.  The replay is queued at the head of its stream's matching: it pins its changes against trimming and eviction, keeps the saved resume token from passing them, and builds its bodies through the body gate.  Until it ends, the joiner is left out of matching and pings, so nothing live is queued to it; then it is matched live from the next change, so its changes arrive in order.  A subscriber that leaves before its replay ends gets no more of it.

### Sending

- S POSTs are in flight at once (`WEBSOCKET_SEND_CONCURRENCY`, default 64), at most one per connection, so each connection's messages go out in order.  Healthy connections take turns in one ring and go to its back after every POST.  New and slow connections share probation, which holds at most 16 slots while a healthy connection waits and may use any free slot otherwise.  Within probation new connections go first, those with no attempt yet before those retried, and slow ones last.  While a healthy connection exists, new ones take more than 16 slots only while more than 8 are free.  The slow ring starts a POST only while more than 8 slots are free, or while it holds fewer than 4; while it has an entry waiting and holds fewer than 4, healthy POSTs leave enough slots free for it to reach 4.  A slow-ring entry that is no longer slow, as when the slow line rose, moves to the back of its ring, checked every 250ms and when it is taken.  A connection whose message has waited 10s since its last chunk goes to the front of its ring, since the client drops a partial message whose next chunk is over 30s late.  A connection whose next chunk would start more than 20s after the previous chunk of its message landed, as after gateway faults or a long wait for a retry token, is closed instead of resuming the message, since that attempt can run to the 5s request timeout; this is checked on a monotonic clock when a hold is set and again before the chunk is sent.  A healthy connection that waits over 5s for its turn is logged, at most once a minute.
- A healthy POST starts only while the frame bytes stay within F, and a probation POST while probation's stay within F/4; either class may start one POST when nothing of its class is in flight.  Once a frame has waited 1s, nothing else of its class starts until it does.
- An attempt by a connection that is not slow is cut once it has run T since its socket connected.  T = max(250ms, 2 x Ref, base), where base is max(250ms, 2 x the connection's own p99) in the frame's size class, or with no history there the global value: twice the 99th percentile of that class's POSTs among the last 8192 completed within 60s, kept within 250ms to 4s, and 250ms with none.  For a healthy attempt base is at most the cap (below).  A response that arrived while the event loop was busy is handled before the cut.  A slow connection's attempts are not cut; they run to the 5s request timeout, or to the hung rule below.
- A cut chunk is aborted: the connection goes to the back of its ring and later resends the same chunk, with the same `_chunkId`, which the client's reassembler ignores if it already has it.  The cut costs nothing, but u keeps counting, so a connection that has not answered within about 1s of attempts turns suspect.  Each abort drops its socket, so a mass hang costs one TLS handshake per cut attempt.
- A cut whole message is released instead: its slot is freed and its frame bytes leave F, the request keeps running, and the connection's next POST waits until it settles.  A 2xx delivers it once, a gateway fault retries it (see Failures), a 410 means the connection is gone, and no answer closes the connection at the request timeout.  Its answer is a latency sample like any other.  At most 20 x S requests and 32 MB are released at once; past that a cut whole message is aborted and resent after 1s, logged with a count.
- The cap holds the healthy rotation, the time a healthy connection waits for its next turn, near 3.5s.  Once a second the raw rotation is the largest of: the longest wait from ready to start among healthy POSTs started in the last second; the age of the oldest waiting healthy entry; and the predicted `(ready healthy + healthy in flight) x H / max(8, S - probation in flight)`, H being the mean slot hold of the healthy attempts that ended in the last second.  R = 0.5 x R + 0.5 x raw.  When the larger of R and the raw rotation is over 3.5s, the cap steps down to `max(250ms, 2 x p90 of the healthy attempts completed in the last second, cap x 3.5s / rotation)`, from the largest healthy base of the last second when no cap is set, and healthy attempts in flight are re-armed to it at once.  When R is under 2.45s the cap rises 25% a second and is removed above 4s; in between it holds.
- Hung rule: a suspect's attempt still unanswered more than `max(2s, 2 x Ref_3s)` after its socket connected counts as hung, and the connection is closed, checked every 250ms.  Ref_3s, per gateway endpoint, is the k-th fastest of that endpoint's attempts that both started and completed in the last 3s, k = min(10, ceil(n/10)); with none the rule is off and the 5s request timeout applies.  Released requests are not suspects, so the rule never applies to them.  A client that answers within 1s is never closed by it.  An endpoint-wide slowdown to 2-5s closes nothing, since attempts started after its onset either complete at the slowed time, which raises Ref_3s, or none complete within 3s.  A slowdown that hits only some connections of an endpoint, while more than k of its attempts keep completing fast, closes the slowed suspects that answer after 2s.
- The connected socket is seen through `diagnostics_channel` `http.client.request.created`: a reused socket counts at assignment, a new one at `connect` or `secureConnect`.  Setup still holds the slot.  A POST with no connected socket after 3s is cut as a gateway fault, and the 5s request timeout runs from connect, with the SDK's own 4s connect and 9s request timeouts as backstops.  Gateway hostnames are resolved through an in-process cache: 30s TTL, all addresses rotated, a stale entry served for up to 5 minutes on a lookup error, and one refresh in flight per host.
- POSTs go through clients that make one attempt per call, one for healthy connections and one for probation, each with `maxSockets` 21 x S + 8 so nothing queues in the agent, released requests included.  Since an abort drops its socket, the separate probation agent keeps those aborts from taking a healthy connection's socket.  The gateway's three clients (healthy POSTs, probation POSTs and `DeleteConnection`) are created at startup and look up their credentials together, so the first deliveries do not wait for the lookup.

### Failures

- 410 means the connection is gone: it is tombstoned (below) and its subscriptions are removed at once, with no `DeleteConnection`.
- A 429, a 5xx, a 403 (below), a network, DNS, TLS or credential error, `ECONNRESET`, `EPIPE`, and a POST with no connected socket after 3s are gateway faults.  The message is not dropped: the connection gives up its slot and holds 100ms, 400ms, 1s, 2s, 4s, then 5s before each retry, and each retry takes a token from a budget shared by all connections (2 x S, refilled at S per second and by one for each successful POST).  The head message's 60s of sending time (see Closing) bounds the retries.
- A 403 to the connection's own POST is a strike, unless a different connection on the same endpoint got a 403 in the last 1s, to a POST, a ping or a `DeleteConnection`.  Three strikes in a row close the connection with the reason "403 not shared by the endpoint".  A 2xx to the connection's own POST resets the count, and so does a 403 that is not a strike; another connection's 2xx does not.  A 403 to a ping counts for the other connections on the endpoint and is never a strike against the pinged one.  So a connection the gateway refuses while it serves the others leaves after three attempts, and a 403 for the whole account closes nothing while traffic is dense, until the 60s of sending time; with one or two active connections, it can close one after three attempts, about 1s.  Two connections refused on their own at the same time can reset each other's counts, and then the 60s applies.
- `ExpiredTokenException` exits the process with an error before any retry, so the service manager restarts it with fresh credentials.
- A request timeout after connect closes the connection, as does any other 4xx, such as 400 or 413, with the error.
- Pings, and deliveries to a subscriber whose endpoint is not this gateway's, are attempted once and settled whatever the outcome.
- Failed sends `warn` once, then with a count every 10s.

### Closing a connection

- A connection is closed once its head message has used 60s of its own sending time: connecting, in flight, released, held after a gateway fault or an abort, or waiting for a retry token.  Time waiting for its turn in a ring or for frame room does not count.
- A connection is closed once its drain, the time to send at L* what only it still holds (POSTs only, not slot waits or pings), has stayed over 60s for 10s in a row, since one slow POST on a cold socket times a deep queue overstates it.  A suspect's drain is priced at L, so one that has never completed a POST has none; a connection slow by L counts every POST it has queued, shared or not.  A fast client that alone has over 60s of POSTs queued, such as after a bulk import into one subscription, is closed and refetches.
- While the stored bytes are over B, a connection slow by L for 10s may be closed for the budget, or one slow by L for any time while a body has waited 1s for room.  Each whose close alone frees at least max(B/1024, (stored bytes - B) / 64) is closed, the one that frees the most first, by a ranking redone at most every 250ms; when none does, they are all closed together if together they free that much.  Healthy connections and suspects are never closed for the budget.  These checks run after each match and every 250ms.
- A close aborts the connection's POST in flight, drops its queue, takes it off every in-memory subscriber list and blocks it, so nothing more is sent to it.  The closes of one check are applied together: one pass per subscription, one write of their records, and one log line per reason with a count.  The pending close is persisted in `subscriberFanoutCloses` ({endpoint, connectionId, firstAttemptAt}, with a 2h TTL index).  `DeleteConnection` goes through its own client: one attempt per call, 16 in flight, 5s timeout.  A 403, 429, 5xx, timeout, network or credential error is retried after 1s, doubling to 60s, with jitter.  On 2xx or 410 the connection is pulled from its subscriptions and its tombstone saved, and only then is the record removed, so a restart before the tombstone is saved sends the close again.  Any other 4xx logs an error and stops the retries, leaving the connection blocked.  `ExpiredTokenException` exits, as for a POST.  At 2h, the gateway's connection limit, the record is removed and the connection is pulled from its subscriptions without confirmation and without a tombstone.  A restart loads the pending closes, blocks their connections and resumes the retries.
- Every connection the fanout has removed is tombstoned in `subscriberFanoutTombstones` ({_id: "endpoint connectionId", endpoint, connectionId, reason, expiresAt}, with a TTL index on expiresAt): a confirmed close until firstAttemptAt + 2h, and a connection answered with 410 or removed as another gateway's until 2h after.  A gateway connection lives at most 2h, so an expired tombstone names no live connection.  Incoming subscriber lists (the watcher's inserts and updates, and the resync) drop blocked and tombstoned connections before they are stored or replayed to, and a list that still names a tombstoned connection has it pulled again, at most once a minute.  A send to a blocked or tombstoned connection, such as one queued from a list read before the close, is dropped at once.  A restart loads the tombstones too and logs both counts.
- Pings go once per subscription, skipping connections that already have something queued, and do not count toward the 60s drain.

### Pausing

- Over B, events held only for replay are evicted first: from the stream whose replay-only events free the most, oldest first, choosing the stream again after each eviction, so a quiet stream keeps its window until the larger ones come down to its size.  While streams are paused, eviction also brings E down to the lowest paused stream's resume line.  The replay buffer keeps at most 500 events and 30s per collection; an event a queued replay has pinned stays until the replay passes it.
- A stream pauses when the read gate refuses it, with h = max(B/8, the refused event's heap).  If E is still over B after the closes and no stream is paused, the stream whose events and deliveries hold the most heap pauses, provided it holds at least max(B/8, e), e being the largest event it has read, with h = max(B/8, e); a stream holding less would free too little to reach its own resume line.
- A paused stream resumes when E falls to its resume line B - h, checked every 250ms.  The line is above 0 for every event the gate admits, since an event over B is skipped.  Once a stream has been paused 10s, it resumes before any other, and what it was refused is admitted against C; meanwhile other streams read only under its line, so each refusal ends after one pause.  It keeps that place until the refused change is admitted, or for a refused lookup until the lookup is, though it reads newer changes meanwhile.  A resumed stream reopens after the last change it took.
- A pause lasts as long as the stream's connections take to drain D bytes, `D = (E at the pause - B) + max(B/8, c)`.  With c the largest event the stream read, m its POSTs per message and k its connections, each connection needs about `D / (c / m)` POSTs and the slots serve at most 48 connections at once (S - 16), so the pause lasts about `(D / (c / m)) x L x max(1, k / 48)`.  Each pause logs this estimate as "P about Ns", with L the median POST of the last minute, or "P unknown" when no POST completed in the last minute.

### Streams and the watcher

- Opens, reopens and resumes take turns: the next starts when the previous one has its first batch or after 2s, with up to 4 at once.  A stream's batch size is 1 MB over the largest BSON size of its last 100 events, between 1 and 1000, and 16 before it has read any.
- Each stream saves its resume token within 5s of its changes settling, and on shutdown (`SIGTERM` or `SIGINT`).  A stream with nothing unsettled or queued also saves the server's post-batch token every 45 to 75s, an interval drawn per stream, so a quiet collection's position does not fall out of the oplog.  At startup the saved positions of collections no subscription watches are deleted.
- A dedicated stream that falls back because of its filter drops the document on the server after the match, and looks it up before matching each change, with majority read concern, once per change for every dedicated stream that read it.  A try has 5s on the server and 6s in all; failed tries are retried after 1s, 2s and 4s, and at 31s the change goes out as its ids-only update with a `warn`.  While lookups keep failing, each later change gets one try before its ids-only update, and a success ends that.  A document whose heap plus JSON size is over B also sends the ids-only update with a `warn`, as does a document that is gone.  Otherwise the document is admitted at the read gate like an event: one that does not fit pauses the stream and is looked up again when it resumes.  It is charged once, against the first event given it, until the last event given it is released.  A slow Mongo holds only that stream and never closes a connection.  A stream that falls back because of its projection keeps its server-side projection and the document.
- A stream that fails is reopened with backoff up to 60s.  Errors that will not pass by themselves, such as a pipeline the server rejects or a missing permission, are logged at `error` on each try.  Removing a subscription waits at most 10s for its stream to close.
- When a stream's resume position has left the oplog, every connection subscribed through it is closed with the reason, so its client reconnects and refetches, and the stream reopens from now.
- A delivery to a subscription with no subscribers left is settled at once, and the subscription is deleted in the background, so the stream's token keeps moving.
- The `querySubscriptions` watcher handles inserts, updates and deletes; a replaced document is picked up at the next resync.  It resyncs at startup, on invalidate (the collection dropped or renamed, or the database dropped) and when its resume position is lost: it reads the cluster time, loads every subscription, registers new or changed ones, unregisters removed ones, drops blocked and tombstoned connections, and watches from that time.  Other errors reopen it with backoff.

### Delivery guarantees

- Delivery is at least once.  The persisted resume token, and a dedicated stream's `lastChange`, never pass a change that is unmatched, whose sends are unsettled, or that a queued replay has yet to send, so a restart redelivers them.
- These lose a message, each with a `warn` or a close: an event over 16 MB or over the budget; a filter or projection that throws, for that subscription; a subscriber whose endpoint is not this gateway's, which is sent one message and removed; a closed connection's queue; a stream whose history was lost, whose connections are closed; and a joiner whose replay window was lost, which is closed (below).  A looked-up document that is gone, over the budget, or not found within 31s sends the change's ids-only update instead of the document.
- Each connection's messages go out in order, with two exceptions, both logged with a count: a reset after the request was written is retried while the gateway may still deliver the first copy, and a whole message aborted past the release cap is resent while its first attempt may still land.  Either can repeat a message or deliver it after the next one.
- A subscriber that joins an existing subscription is sent the buffered changes from a second before it joined, as a new subscription is.  If part of that window was trimmed by age or count, or evicted for memory, before its replay was queued, it is closed so it refetches, 10 at once and then one a second.  The close is recorded when it is queued, so a restart still makes it.

## Q&A

- If we used DocumentDB, does it support change streams, and can it dispatch to functions?
  - Yes, via Amazon EventSources, but then obviously we're pretty locked into DocumentDB.
  - Internally, we could have our own processing function, dispatched either by a long-running (change-stream) subscription, or by an Amazon EventSource linked to DocumentDB.
